## 局部收益、慢进程变化与波动

每条路线有 1,152 个同种子、重复号和进程号的正式计时配对。

| 路线 | 打包局部降时 / 胜次 | 装配局部降时 / 胜次 |
| --- | ---: | ---: |
| 打包 | 55.24%，1147/1152 | 未启用装配优化 |
| 装配 | 未启用打包优化 | 26.82%，1148/1152 |
| 打包＋装配 | 55.25%，1148/1152 | 26.86%，1147/1152 |

打包进入候选处理的比例仍为输入单元的 4.04%，载荷和语义工作量不变；所有路线前沿评分读取均与控制一致。两个局部优化同时启用时仍有效，没有出现类似前沿索引的普遍局部退化。

固定原控制的完整核心最慢进程，组合核心降时中位数为 7.13%，打包和装配分别节省约 118.39 ms、63.35 ms（各自中位数，不能相加当作同一次总收益）；全局核心降时则只有 3.59%。组合整段交换的全局最大值中位降时约 19.19%。全局结束进程变化与尾部波动限制了局部收益向整体收益的转化。

具体保留的不利样本：

- 种子 17、重复 1：组合全局核心慢 2.81%，但原核心最慢进程快 16.18%；新最慢进程变为 rank 33。该进程装配从约 0.232 s 增至 0.723 s，完整交换从约 0.582 s 增至 0.971 s。
- 种子 17、重复 3：组合全局核心慢 5.61%，原核心最慢进程快 7.94%，新最慢进程为 rank 94。
- 装配单项在种子 −1、重复 1 全局慢 22.59%，新最慢 rank 70 的装配从约 0.234 s 增至 0.636 s；种子 41、重复 2 则出现未优化打包段从约 0.109 s 增至 0.482 s。

这些样本说明必须保留所有正式重复，不能剔除慢样本来报告稳定加速。当前计时能定位到慢进程和阶段，不能独立区分调度抢占、内存分配、网络等待或其他系统因素；不把尾部异常直接归因为哈希实现，也不认定 128 进程受到了 512 进程故障的干扰。

打包单项的计算阶段最大值中位变化约 −0.24%，计算不均衡中位数仍约 1.604。组合约 1.590，并不足以证明跨进程负载均衡已解决。这一轮仍是本地通信准备/接收装配优化。

## 512 进程为什么没有结果

启动回执记录退出码 124、耗时约 60.014 s。日志尾部在多个节点出现：

```text
CREATE_EP cmd: Device or resource busy
UCX ERROR Could not create endpoint on glex device #0
[MPI_PREFLIGHT_OK] ranks=512 thread_support=1
yhrun: forcing job termination
```

存在成功标记，但整个启动命令未在限时内正常退出。现有探测器要求“退出码 0 且标记匹配”，所以停止分配复用的行为符合设计。仅从尾部不能确定是探测后退出阶段卡住，还是在超时边界才完成探测；也不能确定端点资源忙的底层原因。不能将成功标记单独当作探测通过，不能把本次记录纳入性能样本。
