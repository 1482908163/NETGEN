# 编号传输与幽灵交换的依赖拆分

**2026-10-07 状态更新：** [真实应用实验结果与研究决定](20261007_ghost_pipeline_results.md)已归档。432 次正式运行及 27 份自然质量报告通过覆盖/一致性检查，但没有形成跨规模、跨分区稳定核心净收益；默认保留 legacy，停止本实现的微调。下文保留提案与复现方法，本轮无需重跑。

本轮基于 `1eaa0d3da7d5a9606f22f2db7bf52ca18dd7772b`，承接 [前沿质量上界实验结论](20261007_front_quality_results.md)。前沿上界方案相对诊断对照的小幅改善没有形成相对 `batch_parallel` 的稳定核心收益。本轮停止继续调这个剪枝条件，转向通信路径中可以明确拆开的数据依赖。A/B 的整域调度、动态前沿并发不在缺乏独立性证明时加入本轮。

## 原理与范围

原路径依次完成：顶点编号交换及解包 → 选择幽灵四面体并打包 → 邻居数量交换 → 幽灵载荷交换 → 按进程顺序写入幽灵网格。

选中哪些四面体、发给哪些邻居、复制哪些坐标，以及各邻居的数量，仅依赖固定本地网格和已经建立的共享顶点邻接表，不依赖远端全局编号。于是将载荷准备拆成：

1. `Build`：按本地单元顺序，保留原“三个相邻顶点”规则、邻居排序与四个顶点坐标；记录本地单元索引和四个顶点索引。
2. `Bind`：编号接收与解包完成后，把当前顶点/单元编号写入已准备的载荷。允许这期间为完整输出进行编号压缩，因为绑定读取最终编号数组，而不是预先保存临时编号。
3. 保留已有载荷交换与按邻居升序解包，写入的网格内容及顺序不变。

`ghost_pipeline` 在顶点编号请求发出后立即 Build，并发出邻居数量请求，再等待编号。MPI 能否在打包计算期间推进实际传输依赖集群实现，本轮不假定后台进度，不引入通信线程或反复轮询。依赖拆分也给邻居数量传输留出更早的启动机会。

| 路线 | 应用参数 | 用途 |
| --- | --- | --- |
| `batch_parallel` | `--ghost-exchange legacy` | 原始批处理基线 |
| `ghost_staged` | `--ghost-exchange staged` | 相同计划/绑定实现，等待编号后才 Build/Bind/发数量；测量重构开销 |
| `ghost_pipeline` | `--ghost-exchange pipeline` | Build 与数量发送提前到编号等待之前；测量依赖拆分收益 |

三条路线的内核都使用 `batch_parallel`：同样的确定性单线程批量细化和恢复批次并行，同样的原生成域、临时 64 位编号、分区、绑定和载荷协议。新路径要求 communication-only、async-global-ids、批量幽灵交换，拒绝与 worklets、mesh-tasks、逐邻居 ready 载荷路径混用。应用默认仍是 legacy。

## 正确性与成本

- Build 不读取任何未完成的编号接收缓冲区。Bind 要求本地点数和单元数不变，并拒绝未解析的非正编号。新计划明确只接受四面体。
- 邻居集合严格复用原数量交换所用的全部粗共享顶点邻接图；包括发送数量为零的邻居。
- 数量请求及其收发缓冲区由不可复制、不可移动的对象共同持有。Begin 后不改写/扩容发送数组，不读取接收数量，直到 Wait 完成。析构若仍有请求会中止 MPI。
- 新编号请求使用固定标签 3818，与数量标签 4821 分离。原来的发送进程号标签不能在这两个协议重叠时继续使用，否则进程 4821 会产生消息匹配冲突。载荷的类型、字段、消息数量和字节数不增加；原路径标签保持原样。
- 每份发送的幽灵单元增加 20 字节本地索引引用（不计 vector 容量及容器开销）。绑定/预热核对后释放引用，载荷函数返回前释放计划载荷。没有新增线上载荷或网格实体。
- 自然计时的质量预热对两个新路径独立重建原串行打包结果，逐一比较邻居、数量、顺序、单元编号、域号、四个顶点编号和坐标 double 位模式。任意不符直接失败。正式实验关闭这次串行重建。
- 原有体网格、方向、质量、边界、临时编号及规范化幽灵网格审计继续生效。

## 测量与门槛

新增指标包含扫描/选中/发送单元数、引用字节数、数量邻居数、提前准备/数量发送覆盖、串行核对次数及核对单元数。分析拒绝阶段缺失、原等待路径回退、无效计数、提前位置错误和核对覆盖不完整。

三路线逐次比较每个进程的顶点/幽灵收发工作量；staged 与 pipeline 还比较逐进程的计划选择覆盖。相同总量不能替代逐进程相同工作。

将 `ghost_vertex_post/wait` 与 `ghost_count_post/wait` 记为通信阶段，`volume_exchange_pack` 与 `ghost_id_bind` 记为计算阶段。`adjacency_exchange_stage_sum_max_seconds` 为**先在每个进程求实际交换相关阶段之和，再取最大值**，包括打包、绑定、等待、准备、解包等，既不是纯传输时间，也不是任意两个全局最大值相减。保存对应进程编号及同进程分解；诊断明细保留原最慢计算进程，并增加该交换阶段合计最慢进程。

优先看 natural 核心时间相对原始基线的逐次胜率、幅度、九个固定规模/分区的稳定性，再用 staged 对照和交换阶段合计判断来源。只有“提前准备”指标通过不等于硬件重叠成功；只快于 staged、没有相对原基线的净收益，也不能升为默认方案。若无净收益，停止沿此路径继续轮询频率等微调。

## 本地验证与实际限制

已完成：

- 5,000 组直接使用生产计划的随机载荷等价检查：重复邻居项、排序、空工作、64 位编号、准备后编号压缩、坐标正负零位模式、状态/未解析编号拒绝。
- 脚本化 MPI 对生产发请求/数量持有类进行顺序、零/不对称数量、缓冲区寿命和标签冲突测试。
- 新预设默认配置、非法统计/阶段/核对覆盖、相同总量但逐进程重新分配的拒绝测试。
- 实际统一 runner 的三路线模拟：三个种子、144 次正式模拟运行，顺序轮转、失败后继续、相同分区覆盖警告；原路线相关回归。
- 两处修改的应用翻译单元使用仓库真实 nglib 声明完成 C++17 语法检查；MPI/METIS/OCC 接口使用本地桩。新真实 MPI 压力测试也通过语法检查。

本环境缺少真实 MPI 与 OCC，**没有完成完整链接或真实多进程性能验证**。新增 `test_ghost_plan_mpi.cpp` 并接入 `tests/run_tests.sh`，覆盖 1/2/3/4/8 进程、大编号消息、延迟邻居、空/不对称幽灵数量及实际载荷核对；实际运行仍须集群。下面的正式预设在同一批次进行真实应用质量预热和性能实验，不要求单独手工拆分提交。
