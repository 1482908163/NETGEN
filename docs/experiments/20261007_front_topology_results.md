# 前沿拓扑索引实验：正确但变慢，停止该路线

## 结论

代码提交 `294f1c4919deac03157cf9857cebaf3af1afa4d4`；结果提交 `36c3b1b3b97897f5dcc3aad6e1aecb0e22c6b02b`。
批次 `mesh_algorithms_20261007-004444`，三规模、三分区、三路线、两种计时模式，各八次正式重复。

432 次正式运行有效，27 份质量审计通过；三个规模的路线和单路线异常文件均为空。同规模、同分区，三路线逐进程质量审计记录完全一致；每个规模每条路线均有三个实际不同的表面归属指纹。诊断控制与候选的每次正式运行，逐进程匹配调用数、映射数、通过类型/质量筛选的规则数完全相同。

实际枚举访问减少 82.58%–83.76%，但固定进程的前沿匹配在九组自然运行的全部 72 个配对中都变慢，配对增幅中位数 8.61%–13.64%。因此不能将访问数下降称为算法加速，也不能用部分整体时间的正波动接受该路线。停止索引方案的继续调参；显式路线保留用于追溯，原 `batch_parallel` 基线继续保留。本次提交仅记录实验结论，没有引入新算法或新实验任务。

| 128 | -1 | 1.70% | -0.92% |
| 128 | 17 | -2.31% | 4.90% |
| 128 | 41 | 2.76% | 5.02% |
| 256 | -1 | -6.30% | 1.30% |
| 256 | 17 | 1.21% | 1.20% |
| 256 | 41 | -6.26% | -4.14% |
| 512 | -1 | -1.88% | -4.27% |

相对同诊断的 `front_profile`，256 进程、种子 41 的自然运行慢 5.36%（八次无一更快），分阶段计时慢 5.71%；512 进程、种子 17 的自然运行慢 6.04%，分阶段计时慢 6.41%。

分析器的 `validated=True` 表示审计、覆盖和配对完整，不表示性能显著改善。并行作业环境下，阶段外耗时也发生波动；例如纯诊断控制相对基线也出现正负几百分点的变化。不能把自然核心时间的零散正值归因于一个已被同进程计时证明变慢的前沿机制。

对每个配对计算 `候选匹配时间 - 候选构建时间 - 原匹配时间` 后，九组的中位数仍为正，约 1.66–16.61 毫秒。构建累计时间包含在匹配累计时间内，可在同一次同一进程记录中扣除；这项扣除仅作成本诊断，不代表存在一个无需构建的可运行方案，也不等于独立测量了查询耗时。

## 原因与下一步约束

已证明：本模型的索引机制正确、减少实际枚举访问，但前沿匹配变慢。

源码解释支持：索引只跳过原先在已映射顶点比较中就会被拒绝的组合。这些拒绝原本主要是顺序数组读取、少量整数比较和短路退出。索引保留全部有效候选的顺序，后续几何距离、自由区变换及相交测试、新单元质量评估仍按原序执行，因而没有减少这些昂贵计算。新路径另付出每次调用构建关联表、查询和游标管理的成本。访问数量减少不等于有效几何工作量减少。

没有测得每一种几何检查的独立耗时，不能断言自由区相交测试就是唯一瓶颈。现有同进程数据指出：前沿在 256/种子 41、512/种子 17 上有可观绝对耗时，而其他分区的优化、修复和 Delaunay 阶段也有不同占比。下一方案应针对昂贵工作本身，证明能减少实际几何调用，或者证明原域内任务之间可以独立执行；不能继续围绕索引容器、旋转缓存和阈值做一轮轮微调。

A 路线仍保留原域与归属，C 路线继续保留已有异步编号与邻接实现；这次 B 路线的前沿枚举候选被否决。该结果不意味着负载不均衡问题已解决，也不需要重跑同一预设。
