# 候选反向映射：实现与一次实验说明

本轮基于 `49070f7324901b07867083d8747f47cee770a34f`，在 `agent/load-balance-research` 上继续。状态：实现完成，本地检查通过，尚无本轮集群性能结论。

## 研究问题与边界

上一轮完整规则成本诊断显示，面扫描有可观成本，但高频细分计时本身也有明显开销。因此本轮直接减少面扫描里的重复编号搜索，正式运行仅保留共同的工作计数和既有整段计时。

这是 B 路线内部的局部数据结构优化；它没有改变任务分配或进程间调度，不能单凭比较次数减少就声称解决负载不均衡，更不能据此声称论文创新点成立。A/C 路线既有结论不被本轮替代。

## 改动原理

原实现：对每个与自由区包围盒相交的未使用面，其每个顶点都线性扫描 `pmap[1..GetNOldP()]`，找对应规则点编号。重复映射时，原循环取最后一次命中。

新实现：每个完整候选第一次确实需要查找时，建立局部点编号到规则点编号的反向表；该候选后续查询直接索引。规则编号递增写入，保持最后命中语义。越界编号回退原线性比较，不猜测结果。

- 表仅在一次 `ApplyRules` 调用内复用，跨候选只清理上次写过的位置。
- 完全不需要查找的调用不分配表；不跨调用缓存，不改变候选、面或几何判断顺序。
- 若一个候选有 Q 次查询、K 个旧规则点，原查找为 O(QK)，新查找为 O(K+Q)，另有清理成本；首次使用还有与局部点数成正比的零初始化和存储。候选很小或查询很少时可能得不偿失，必须看整段耗时。
- 建表、清理、首次分配、释放和计数归并都在既有规则/前沿计时内，不仅计直接查询。

涉及 `ruler3.cpp`、新头文件 `front_point_lookup.hpp`、参数转发、新独立接口 `Ng_GenerateVolumeMeshFrontLookup`、应用选项和统一实验分析。原接口签名保持兼容，其他路线默认不开启反向查找。

## 正确性与测量

预热时反向路线执行一次候选版本，再从原始状态完整重放线性 `ApplyRules`：比较返回值、浮点结果位模式、点/面/单元/删除列表、规则命中与可用状态、自由区历史、质量极值和问题记录。参考重放计数隔离；异常后恢复候选状态。任何不一致均使验证失败。

两个路线均采用同样的固定点修复、活跃分裂和有序邻接基础。线性对照也带有共同的工作计数，因此这是本轮两实现的配对比较，不是相对最初未插桩代码的端到端加速比。

| 路线 | 预热 | 正式运行 |
|---|---|---|
| `lookup_linear` | 原线性查找及共同质量检查 | 原线性查找 |
| `lookup_inverse` | 反向查找与完整状态重放 | 反向查找，无参考重放 |

不同时开启规则细分计时、投影变换或连通分量实验。完整质量记录必须一致；即使某项质量看起来更好，也不能接受语义漂移。每个进程分别核对规则调用、候选、发生查询的候选、查询数、原线性比较数，以及邻接和规则工作；全局总量相同不能掩盖进程间工作转移。

新增 14 项指标：`calls`、`candidates`、`queried_candidates`、`queries`、`baseline_comparisons`、`linear_comparisons`、`direct_queries`、`table_builds`、`table_writes`、`table_clears`、`table_bytes_peak`、`verified`、`mismatches`、`reference_seconds`，统一带 `front_lookup_` 前缀。

`table_bytes_peak` 是单次规则调用所持两容器容量的最大值，跨进程仍取最大；不是进程驻留内存，也不是并发调用内存总和。`baseline_comparisons` 是依照相同访问序列推导的原循环比较次数，不等同于节省的时间。

## 一次运行

从已有工程目录执行；本轮改动内核，需要重新编译：

```bash
cd ~/cjz/NETGEN && \
git switch agent/load-balance-research && \
git pull --ff-only && \
cd test_code_expansion && \
bash build_project.sh && \
EXPERIMENT_PRESET=front_lookup bash strong_scaling/run_experiments.sh
```

默认 128/256/512 个 MPI 进程，每节点 4 进程、每进程 4 核；对应 32/64/128 节点。三个分区种子 `-1/17/41`；每路线每种子一次质量预热、三次正式重复，共 72 次启动（54 次正式运行）。沿用原输入及网格细化配置；不同规模并行提交、统一启动时刻，同规模内轮换路线顺序。

单次运行默认超时 600 秒，显式 `TIMEOUT_SECONDS` 覆盖仍有效。超时、被杀以及已识别的 PMIx/作业步创建故障会停止**当前作业分配**中的后续启动，退出码 75；其他独立规模不受影响。普通应用/质量失败继续其余可运行任务；质量预热失败会跳过依赖它的正式运行。保留失败证据，清除过时的性能汇总，不能把未完成批次当作成功。

## 输出与判断

每个 `p128/p256/p512` 汇总目录新增：

- `FRONT_LOOKUP_SUMMARY.txt`：中文摘要。
- `front_lookup_fixed_rank_pairs.csv`：每个线性对照原计算最慢进程，与反向路线同一编号的完整配对。
- `front_lookup_summary.csv`：按种子汇总核心、固定进程计算、前沿、规则的配对降幅中位数及胜出次数。
- `front_lookup_sources.json`：质量记录和逐进程证书的哈希。

每次运行保留 `front_lookup_certificate.csv` 和压缩原始进程数据；分析时交叉复核，不能仅修改汇总数字得到性能结论。完整规则耗时包含在前沿耗时内，两者不可相加。

判断顺序：先看是否全部有效、是否同质量同工作，再看固定进程规则及前沿是否下降，最后看核心时间是否稳定下降。仅查询比较减少或某一次胜出不构成收益。如果表构建成本抵消查询收益，或者收益无法传导到核心时间，应关闭该路线，回到真正的关键路径，不围绕表大小反复调参。每组三次重复仅作首轮筛选。
