# 保持原编号与单元顺序的批量体细化

## 依据和定位

基于结果提交 `13273dbe87bb05803d9cac4b8ebb690826e6af11`，诊断批次 `mesh_algorithms_20260929-021801`。
旧 C 在 128/256 进程的固定慢进程 19/155 上，体细化时间中位数约 0.683/0.353 秒。
该阶段明显大于已否定的恢复候选评估，并且在两个规模上都存在。

本次实现 A 的域内独立细化工作单元；没有新增几何切面、改变逻辑归属或转移整个生成域。
尚未实现跨进程窃取或 B 的同步关键路径调度。先验证独立任务是否真正缩短计算时间，再考虑资源协作。
C 的编号与邻接交换保持已验证方案。

## 算法

原程序逐体单元查询有序边表，首次发现边时创建中点，再逐个追加 8 个子四面体。
这个顺序同时决定共享中点编号和输出单元顺序，不能直接并行改写共享边表。

新路径保留原表面细化，然后对体单元执行：

1. 保存原四面体连接和材料编号，为每个父单元生成 6 条边记录及原始访问序号。
2. 分段排序、分层归并，按端点对分组。与已有边表顺序合并，复用已存在的中点。
3. 新边按最小原始访问序号分配连续编号，恢复原程序的首次遇边顺序。
4. 串行预分配点和单元数组。并行写入独立中点及子单元位置：子单元 0 覆盖原父单元位置，
   子单元 1..7 按父单元顺序放到原数组后部。沿用原 8 子单元连接表。
5. 主线程按端点排序顺序更新调用方边表，保留全部历史项。统一更新网格时间戳。

网格修改期间不扩容共享数组；已有点只读，新点和新单元各由唯一任务写入。
原生新增点的层号/类型、单元材料及追加单元标志按原接口保持。
不调用改变几何、平滑点或重新剖分的算法。

新接口 `Ng_RefineVolumeDeterministic` 只接受四节点四面体、合法有序边表和局部索引范围。
失败会终止该次运行，不回退后继续使用部分修改的网格。
局部索引仍为现有的 int 容量；全局 64 位临时编号方案保持不变。

## 单批消融

新增 `EXPERIMENT_PRESET=refine_bulk`，三个路线均使用旧 C 通信和 4 线程体生成/修复：

| 路线 | 体细化 |
| --- | --- |
| `async_global` | 原逐单元边表查询与追加 |
| `refine_serial` | 新批量算法，细化线程数为 1 |
| `refine_parallel` | 同一批量算法，细化线程数为 4 |

因此旧 C → 单线程隔离数据组织变化，单线程 → 多线程隔离并行执行，总对照检查净收益。
表面细化仍使用原路径。默认 128/256 进程、每节点 4 进程、每进程 4 核；自然/拆分计时各 8 次正式重复、1 次预热。
总计 96 次正式运行、12 次预热；自然预热执行质量、体网格指纹及真实临时编号邻接审计。
沿用并行提交、统一启动延时、路线轮换、失败后继续和结果清理。

## 诊断与验收

新增输入封装、快照、规划、数组写入、边表提交时间，以及中点数、边访问数、调用次数和线程组启用次数。
这些字段也保存在 `critical_rank_breakdown.csv`，用于检查同一慢进程。
显式规划缓冲区容量按调用累加记录，排除排序临时空间、网格和调用方缓冲；它不是峰值内存或 RSS。
新算法用额外连续缓冲换取排序、去重及独立写入，不能宣称一定降低内存。

分析器验证每次细化恰好执行、线程模式匹配、每轮单元数乘 8、每个父单元恰有 6 条边记录，
分项耗时不得明显超过完整体细化阶段（不同计时源容忍 5% 加 1 毫秒误差）。零次细化只用于流程测试，不支持性能收益结论。

所有路线必须与旧 C 保持体网格和邻接指纹一致；不能降低质量门槛来换取速度。
性能判断同时看同一慢进程的体细化、最大计算时间和自然核心总时间。
若规划/边表维护抵消收益，按分项决定是否保留批量或并行路径，不直接增加调度启发式。

## 本地验证与限制

- 180 组单/多线程对照，包含连续两轮细化、共享边、表面已存在中点、历史边表、空输入及不同完成顺序。
  新规划器与独立实现的原顺序算法逐项比较中点编号、完整边表、全部子单元连接及数组位置。
- 非法连接、重复/乱序边表及局部点编号溢出拒绝测试。
- 地址和未定义行为检测运行上述实际规划器测试；当前环境不支持泄漏检测，已单独关闭该项。
- 修改的 nglib 和应用通过 C++ 语法检查，应用侧 MPI/OCC 为接口替身。
- 三路线模拟批次覆盖单规模 48 次正式运行、质量门槛、诊断计数、结果保留、路线轮换和失败后继续。

没有本地真实 MPI/OCC 全链接环境；实际 Mesh 对象上的几何一致性、内存和性能仍由集群实验确认。
