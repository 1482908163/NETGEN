## 分析脚本错误及修复

原载荷预热的应用日志显示正常生成和结束，但后处理报：

```text
communication baseline requires one complete local mesh per rank
```

上一轮把字典准备、解码、释放三项加入 `COMPUTE` 总计后，仍使用整个集合检查“所有阶段必须各调用一次”。原载荷路线根本不执行这三项，因而六次原载荷预热被误判，十八次依赖的正式对照被跳过。这是分析脚本错误，不是用户运行方式错误，也不是已观察到的网格生成失败。

此前合成测试自动按同一 `COMPUTE` 集合创建测试阶段，给原载荷填入了实际不存在的字典阶段，掩盖了错误。本次修改：

- 明确区分六项共同生成阶段和三项可选字典计算阶段；通信基线和历史阶段模型继续强制共同阶段各调用一次。
- 时间总计仍包含实际执行的字典阶段；字典准备/解码/释放及元数据、接收参考覆盖由字典协议单独检查。
- 原载荷执行字典阶段、没有协议却出现字典阶段、正式出现参考阶段，均拒绝；没有放宽真正缺少生成阶段的条件。
- 测试样本固定应用原有的六阶段，独立于分析器集合。明确复现旧误判，逐项删除共同阶段仍失败，原载荷不执行字典阶段时应通过。
- 历史全路线测试只使用其支持的历史样本；组件、投影、规则、查找、工作空间和字典协议由现有独立样本及专门测试覆盖，避免生成错误协议元数据。

修复后的字典统一入口通过 24 次合成启动及完整质量门槛。历史矩阵通过 220 次正式记录验证，故意注入的质量、编号和缺失记录仍被拒绝；工作空间统一入口及相关验证回归通过。这些是脚本/协议测试，不是性能数据。

## 512 进程启动故障

128/256 启动检查分别约 3.90/3.80 秒完成。512 进程作业 `6090279` 在 60 秒启动检查中被拦截，日志保留：

```text
pmixp_p2p_send: cn7486 [81]: ... send failed, rc=111, exceeded the retry limit
Cannot send message to /tmp/slurmd/stepd.slurm.pmix.6090279.0
```

这是 PMIx（进程管理接口）启动通信失败的线索，未进入网格实验。不能据此判断字典传输在 512 进程上的性能，也尚不能将具体节点或配置认定为最终根因。启动检查避免了继续重复启动网格及等待原 600 秒网格预算。
