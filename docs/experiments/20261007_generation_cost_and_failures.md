# 生成、修复全成本诊断与失败证据保存

分支：`agent/load-balance-research`。本轮基于 `b7e06a5f4b8da54f8a33bafe0bdde1defcde8ae2`，承接 `mesh_algorithms_20261007-195529` 的实测分析。

## 本轮决策

停止继续微调有序边合并提交波次。上一轮 40 组固定进程的自然计时配对全部变慢；原串行提交只有 0.111–6.091 ms，规划就耗费 0.444–7.531 ms。原提交仅占最终优化的 0.12%–0.90%，即使彻底消除也无法解决主要长尾。

另一个候选是 Delaunay 相交过滤，但上传记录中的该项只有约 0.8–9 ms。暂不为它新增并行实现。已有记录反而显示生成、修复中的完整 Swap/Split 操作有几十至几百毫秒的成本，需要先弄清其准备、评价和提交分别占多少，以及评价时任务团队是否已经可用。

下表来自上一轮 `combine_profile`，每行固定同一个计算长尾进程，取 8 次正式自然计时的中位数，单位 ms。它们是**完整操作的包含式主机计时，不代表串行成本**，也不能把不同进程的各项最大值拼成一个进程的时间。

| P / seed / rank | 生成 Swap | 生成 Split | 修复 Split | 修复 Swap | 最终 Swap2 |
|---|---:|---:|---:|---:|---:|
| 128 / -1 / 19 | 363.37 | 156.62 | 131.12 | 132.25 | 158.90 |
| 128 / 17 / 3 | 450.93 | 187.31 | 126.59 | 137.65 | 122.18 |
| 128 / 41 / 62 | 364.74 | 127.75 | 116.61 | 127.90 | 126.13 |
| 512 / -1 / 454 | 96.59 | 30.93 | 26.19 | 31.66 | 29.78 |
| 512 / 17 / 359 | 64.57 | 13.89 | 14.46 | 7.84 | 14.90 |

因此本轮交付是一次成本定位和故障定位迭代，**尚未实现或证明新的算法加速**。新路线 `cost_profile` 使用 `batch_parallel` 的算法、资源和提交顺序，增加完整操作的计时与计数。对照只用于估计诊断开销。

## 新增成本记录

新增 `Ng_GenerateVolumeMeshCostProfile`，独立输出 252 项数据，不扩容旧接口的数组。安装头文件清单也包含新的 `volume_cost_profile.hpp`，避免应用读取已安装头文件时漏依赖。

布局为 3 个阶段 × 4 个操作 × 21 个字段：

- 阶段：`generation / repair / optimization`。
- 操作：`combine / split / swap / swap2`；`swap2` 指面交换操作。
- 顺序字段：`total_seconds, prepare_seconds, evaluate_seconds, order_seconds, commit_seconds, cleanup_seconds, calls, input_points, input_elements, evaluated_items, candidates, commit_attempts, applied, team_evaluations, quality_seconds, conform_seconds, rest_seconds, worstcase_seconds, legal_seconds, serial_evaluate_seconds, team_evaluate_seconds`。

每个操作的准备、评价、排序、提交、收尾五项之和等于总时间；按质量、符合性、恢复、最坏情况、合法性五个优化目标汇总的时间是另一种总时间划分，不能再与前五项相加。评价时间另按调用时是否有可用多线程任务团队划分。

这些都是主机墙钟时间，包含同步等待工作线程。`team_evaluations` 表示调用评价前任务团队可用，**不证明每个线程实际参与，也不是 CPU 时间**。`input_points / input_elements` 累加各次调用时的网格规模，不是唯一单元数量，也不是实际扫描次数。实际进入评价的项目、候选、提交尝试和成功修改另有计数。

计时只发生在操作和阶段边界。几何评价的内部循环没有逐项目时钟；Swap/Swap2 的访问计数每个原任务范围归并一次。关闭诊断时不执行这些计时和归并。诊断路线仍需用对照测量其额外开销。

分析器检查每个进程的全部字段，拒绝缺项、负值、非有限值、非整数计数、阶段/目标/评价时间不守恒，以及 `applied > attempts > candidates > evaluated` 等不一致。当前路线的四类完整操作在各阶段顺序调用，合计还必须落在同一进程的阶段时间内。

输出包括：

| 文件 | 用途 |
|---|---|
| 每次运行的 `operation_cost_profile.csv` | 所有进程 × 12 个阶段/操作组合，包括未执行操作的零行 |
| `route_cost_profile/p*/analysis/volume_operation_costs.csv` | 汇总预热和正式重复的全部进程成本 |
| `critical_rank_breakdown.csv` 中的 `cost_*` 字段 | 当前计算长尾进程的完整成本 |
| `route_cost_profile/**/rank_profiles.jsonl.gz` | 保留可复算的压缩原始记录 |
| `p*/route_comparisons.csv` | 基线与诊断路线的开销配对和质量门槛 |

成本 CSV 同时携带阶段、核心和计算时间、source revision、应用/内核/ngcore/input 的 SHA256。根目录和应用目录的上传忽略规则均已放行 **cost_profile 路线的压缩原始记录**。

质量预热要求两路线的完整质量报告除 `scheduler` 名称之外完全一致，包括各进程记录；仅有汇总指纹一致或质量未退化不够。计时记录继续使用原有输入、划分、资源、编号、邻接和失败检查。

## 自动保存崩溃位置

上一轮有 21 次 P256 根异常集中在 cn483 的 rank 54，且三条路线均出现；另有一次 P512 在生成阶段失败。前者是重要定位线索，尚不能认定硬件故障；后者也不能归因于随后才执行的边合并波次。137 退出码可能来自连带终止，不能单独证明 OOM。

新增 `diagnose_failures.py`，在两处自动调用：

1. `build_project.sh` 构建覆盖旧 ELF 之前，选择最近一个含失败的历史批次，尝试解析旧地址。
2. 实验启动器收到非零退出码后立即解析当前失败，保存证据并继续后续运行。

解析必须同时满足日志中的库/应用规范路径对应和记录的 SHA256 与当前 ELF 匹配。缺少旧 hash、库已被覆盖或无符号信息时明确记录跳过或无源码行，不拿新库解释旧地址。旧批次未记录 ngcore 身份时不会猜测。

支持共享库/PIE 的 ELF 相对偏移、符号加偏移，以及非 PIE 可执行文件的固定虚拟地址；每个对象批量调用一次 `addr2line`，保留内联帧。输出 `failure_symbols.json / failure_symbols.txt`，包含 ELF 身份、源码版本、根异常文本和解析结果。路径/函数/行号必须对应报告记录的源码版本阅读。

若能读取作业信息，同时保存 `scheduler_diagnostics.json`，记录 `sacct / scontrol` 输出。这是采样时的作业状态，可能尚未终止；不是自动确定的根因。命令有超时，诊断失败不会阻断构建或其余实验。

内核继续用 Release、`-O3 -DNDEBUG`，只增加 `-g1` 行号信息，未改用改变优化级别的构建类型。应用原构建已包含 `-g -O3`。本轮没有声称修复上述崩溃。

## 下一步的决策门槛

先检查质量完整一致、正式重复完整、成本守恒和诊断覆盖，再评估诊断开销。选择目标时固定同一进程比较，并看它对计算关键路径的贡献和可消除成本。

- 若生成/修复的准备、排序、提交明显占据长尾，围绕对应数据结构和实际依赖设计批处理、减少重复扫描或受限并行；先列清读写集合，保持原质量及提交语义。
- 若大部分评价时间已经处于有任务团队的调用，不能再以“它是串行”为理由并行一次。应检查可拆工作量、同节点闲置资源和评价范围分布；现有计数不能直接证明线程失衡。
- 若四类操作并非大头，使用同批的 native/phase 数据转向未覆盖的昂贵操作，不在本目标上持续微调。
- 崩溃先按匹配 ELF 的源码位置和各路线共性定位；如果确有内存/索引破坏，再针对证据实现修复和复现验证。
- 执行负载均衡与内核实际工作减少仍是主线；通信流水线保留已验证实现。本轮未重新启用已收束的低收益路线，也未调整模型样本。
