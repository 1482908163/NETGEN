# 同一局部网格内的候选调度原型（2026-09-09）

## 研究状态与依据

工作仓库迁移到 `1482908163/NETGEN`，起点为 `429a378d641a8acd7cab6fa5c8cc852c8e6b37b0`，研究分支为 `agent/load-balance-research`。上传版本仍含旧任务默认配置，因此本次先移植旧仓库 `3ea47f6c05fe77c001302b30bf67b410b22aed5d` 固化的通信基线。已有数据不重写；历史来源见 [任务实验结果](20260909_task_results.md) 与 [通信固化记录](20260909_sparse_baseline_and_new_directions.md)。

稀疏通信的收益已有大规模实验支持。封闭子域任务化改变了实际建网工作量，调度开销及新增边界抵消收益，因此退出默认流程。本轮保持一进程一个局部网格，探索网格内部可分配的工作。

源码核对纠正了一个前提：Netgen 的 `improve3.cpp` 已经并行评价边合并、拆分和交换候选，并按 `(badness, edge_index)`（质量变化、边序号）排序，随后串行修改网格。`meshtype.hpp` 中默认 `parallel_meshing=true, nthreads=4`；单独设置 `OMP_NUM_THREADS=1` 不能证明这些内部工作只有一个线程。历史二进制的实际线程配置不能由新源码倒推。

## 本轮实际算法

实现位于 `netgen/libsrc/meshing/improve3.cpp` 的 `ForVolumeCandidates`，仅替换 `CombineImprove`、`SplitImprove`、`SwapImprove` 的候选评价调度。

对边 e=(a,b)，用端点关联的体单元数 d(a)、d(b) 构造代价代理：

`w(e) = max(1, (d(a)+d(b))²)`。

代理反映局部邻域扫描与拓扑比较规模，尚未证明能准确预测耗时。设当前工作线程数为 T，总代理代价为 W，按原边序连续分块，目标块代价为 `max(1,W/(32T))`。各线程通过原子计数器动态领取下一块，调用原候选评价函数。单个昂贵候选不再拆分。少于256条边或只有一个线程时回退原调度。

构造需要两次 O(E) 扫描；块列表约 O(T)，没有 O(E) 前缀数组，也不创建额外封闭子域。所有规划和领取成本均包含在局部体网格调用和整体核心时间内。保留原候选排序、串行网格修改及质量评价规则，不并发插入或删除单元。

原调度已有任务池：因此新旧对照检验的是“邻域代价分块加细粒度动态领取”的联合策略，不是从串行到并行，也不是将首次使用动态任务池作为贡献。若联合策略有效，后续才值得消融代价分块和块粒度各自的作用。

## 能解决和不能声称解决的问题

本原型尝试降低同一进程内候选评价的线程尾部等待，继而缩短局部体网格阶段。没有实现跨 MPI（消息传递接口）进程的任务迁移，也没有直接均衡全部局部分区。推进前沿、串行拓扑修改及其他未改动阶段可能仍占主要时间。若优化阶段占比小，即使候选评价加速，对整体核心时间的收益也有限。

这只是需要实验检验的算法原型，不能据此声称解决了12.93秒的进程到达等待，也不能直接宣布论文创新成立。已有并行评价、加权分块和动态领取均是已有思想；本流程中特定代价、依赖保持方式及整体收益需要与相关方法比较后才能确定贡献。

## 接口、计时与构建

新增 `Ng_GenerateVolumeMeshKernel`（指定线程和候选调度的体网格接口），验证参数并局部保存/恢复网格参数；旧接口保持原调用路径。新接口分别测量生成、非法单元修复、质量优化三个阶段。外层 `local_volume_mesh`（局部体网格总阶段）还包含局部尺寸场及接口开销，不强制等于三个子计时之和。多进程汇总分别取各阶段最大值，它们不相加冒充关键路径。

公共 `Ng_Meshing_Parameters` 布局未修改，但内部 `MeshingParameters` 增加字段，因此必须重编本仓库内核及应用。沿用 `test_code_expansion/build_project.sh`，顺序构建内核和应用，安装到原 `NETGEN/install`。内核库内容哈希进入运行记录和续跑签名，缺库即停止。新调度只在显式启用内核实验时运行，通信实验默认继续走原接口。

## 用户只需沿用原入口

1. 在 `NETGEN/test_code_expansion` 执行 `bash build_project.sh`。
2. 将 `strong_scaling/run_experiments.sh` 顶部 `EXPERIMENT_PRESET` 的默认值从 `production` 改为 `kernel`。
3. 在 `strong_scaling` 目录执行 `bash run_experiments.sh`。

参数仍统一在脚本开头修改，不另建提交入口。

| 首轮项目 | 默认设置 |
|---|---|
| 节点 / 进程 | 1节点，1个进程 |
| 每进程预留资源 | 固定16核，并绑定核 |
| 内核线程数 | 1、2、4、8、16 |
| 调度对照 | static（原调度）、cavity（本轮调度） |
| 通信与计时 | sparse（稀疏通信）、natural（自然计时） |
| 几何 | 原 wholewall3solid.STEP；细化参数 LEVELS=1、REFINES=1 |
| 重复 | 每组1次预热、5次正式；合计10次预热、50次正式 |

实际单元数由运行输出确定，不预先宣称固定千万或百亿规模。不同进程数会改变分区及实际网格工作量；后续扩展到多节点时仍需记录实际单元数。1线程两种调度因回退逻辑相同，可作为噪声参照。预留资源固定，所以跨线程对照不是资源用量相同于传统每线程一核的强扩展指标。

先看结果根目录 `p1/RESULT_SUMMARY.txt`，需要详细数值再看同目录 `kernel_summary.csv`。每组原始摘要保留在 `kernel_<scheduler>_t<threads>/p1/analysis/`；压缩测量数据和清理中间网格沿用已有逻辑。单元数量差异会标为异常，但数量相同不能代替边界与质量核对。

首要判据为同线程下整体核心时间的重复运行净收益，其次看生成/优化占比和变化。若新调度稳定变慢或优化占比过小，应停止扩展这一路径，并据真实内部阶段成本选择下一处可并行操作；不继续增加轮次或调参掩盖整体退化。多个规模作业仍按既有并行提交与统一延时运行，同一节点内的对照组合依次执行。
